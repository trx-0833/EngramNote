## 1. 问题一：余弦相似度作为"关系判定"的根本局限

### 1.1 它衡量的是"主题相似"，不是"关系"

余弦相似度回答的是 **「这两段文本在语义空间里靠得近吗」**。
而"关系"回答的是 **「这两个知识点之间存在哪种有向、有类型的语义联系」**。
两者**不是同一个量的粗细版本，是不同的量**。

一个形式化的说法：余弦是**对称的**（`sim(a,b) = sim(b,a)`），
而你要的 `prerequisite` / `subsequent` **是有向的**。
一个对称函数**在数学上不可能**表达一个非对称关系 —— 这不是精度问题，是**值域问题**。
（`contrast` / `related` 是对称的，余弦勉强够用；有向关系它连表达都表达不了。）

### 1.2 为什么"主题相似 ≠ 有关系" —— 你自己库里的三个反例

**反例 A：重复 ≠ 关系。** 相似度 **1.0000** 的 Top 对，标题**完全相同**：

```
1.0000 [跨篇] '开关操作术语'                × '开关操作术语'
1.0000 [跨篇] '注明日期引用文件的适用规则'   × '注明日期引用文件的适用规则'
```

真库实测：**72 种标题重复、涉及 187 张卡（5.4%）**。两张卡讲的是同一件事，
但"同一件事"该**合并**，不该连一条"相关"边。**把重复当关系存下来，
等于把数据质量问题藏进图谱。**

**反例 B：同领域 ≠ 有关系。** 两份不同的电力技术标准，用词、句式、术语体系都像，
余弦自然高，但讲的是**不同对象**。仓库的盲判 v2（每格 24 对）实测：
跨笔记对在**每一个余弦层**都劣于同笔记对（`docs/journal/relation-quality-2026-09-26.md` §9.4）。

**反例 C（最关键）：真正有关系的对，分数反而更低。**

```
0.6748 [同篇] '电力工业发展概况' × '新中国成立前电力工业状况'
0.6725 [同篇] '电力工业发展概况' × '2013年电力工业成就'
0.6564 [同篇] '电力工业发展概况' × '电力规划的定义'
```

这些是**总述 ↔ 分项**（典型的前置/父子结构），正是你想在图谱里看到的边 ——
却只有 **0.62~0.67**，全部低于 0.75。而重复卡是 **1.0000**。

> **在这个语料里，"重复"比"有关系"更相似。**
> 用单一相似度阈值同时区分「重复 / 有关系 / 无关」是**做不到的**。

### 1.3 机制解释：为什么分数会挤在一起（这是根因，不是玄学）

我实测了各向异性（真库 3469 张 bge-m3 向量）：

| 度量 | 实测值 | 各向同性基线 | 结论 |
|---|---|---|---|
| 平均向量 L2 范数 `\|mean\|` | **0.7049** | 0.0170 | 所有向量挤在**同一个锥**里 |
| PC1 解释方差占比 | **5.02%** | 0.098% | 存在**一个压倒性的公共方向** |
| PC1..PC10 累计 | **27.28%** | 0.98% | 少数方向吃掉四分之一方差 |
| 成对余弦 P50 / std | **0.4934 / 0.0784** | — | 动态范围被压缩 |

**机制**：`|mean| = 0.70` 意味着任意两张卡的向量**天然就共享 70% 的方向**。
这个公共分量**与内容无关**（它来自模型本身 + 你语料的高度同质性：
同领域、同体裁、术语反复出现，且嵌入文本中位仅 **53 字**）。
它给每一对都加了一个**接近常数的高基底**，把真正有区分力的信号
压缩进一个很窄的残差里 —— 于是：

- 最近邻中位 **0.8653**、**80.2% 的卡**最近邻 ≥ 0.80（阈值失去分辨力）
- 想让多数卡连上 → 阈值降到 0.6 → 人人连人人
- 想让边精确 → 阈值抬到 0.95 → 绝大多数卡重新孤立

**这不是参数没调好，是信号的信噪比问题。** 且**有成熟的、CPU 上就能做的修法**（见 §4 P1）。

### 1.4 还有一层：卡片太短，本身就判不出关系

真库实测卡片长度：

| | 中位 | P90 | 均值 | 最大 |
|---|---|---|---|---|
| `content` 字符数 | **40** | 89 | 49 | 914 |
| `title` 字符数 | 12 | — | — | 42 |
| **嵌入文本**（title + content[:200]） | **53** | 101 | 61 | — |

**中位 40 字。** 这个长度下，嵌入向量实质上是一个**术语袋**：
它编码"这张卡在讲什么话题"，几乎不编码"它与其他知识点的结构位置"。
而 `CONTENT_EMBED_LIMIT = 200` 的截断**只影响 23 张卡（0.66%）** ——
**截断不是问题，短本身就是问题**。

> 这也解释了为什么**换更大的模型收益有限**：bge-m3 已经是 C-MTEB 上的强模型，
> 瓶颈不在编码器质量，在**输入信息量**与**任务定义错配**。

## 2. 问题二：能真正判定"关系"的方法对比

> 评级口径：**✅ 可行** / **⚠️ 有条件** / **❌ 不适用**。
> 代价按本项目环境估（CPU-only、2.6~4 GB 可用、SQLite、可调云端 LLM）。

### 2.1 总表

| 方法 | 解决什么问题 | 需要什么输入 | 本场景可行性 | 代价 |
|---|---|---|---|---|
| **A. 嵌入余弦（现状）** | 主题召回 | 文本 | ✅ 已在用 | 全量矩阵 71 ms / 0 存储增量 |
| **B. 嵌入 + 各向异性后处理**（白化 / 去主成分） | 让余弦**恢复分辨力** | 全库向量（一次性统计） | ✅ **强推** | 4.2 MB 常数 + 37 ms 变换 |
| **C. 有监督关系抽取（RE）** | 抽取**指定类型**的关系 | **标注数据** + 实体识别 | ❌ 无标注、无实体层 | 标注成本不可承受 |
| **D. 开放域关系抽取（OpenIE）** | 从**句子**抽三元组 | 完整句子 | ❌ 卡片中位 40 字，无完整句 | — |
| **E. LLM 成对/批量判定** | **类型化**关系 + 方向 | 候选对 + prompt | ✅ 已有网关，**但必须召回前置** | 见 §2.4 |
| **F. 图结构链路预测**（共同邻居 / Adamic-Adar） | 给候选**排序**、零模型成本 | 已有边 | ⚠️ 当前图太稀疏，**只能当排序特征** | ~0 |
| **G. 知识图谱嵌入**（TransE/RotatE） | 补全**已知类型**的边 | **大量已类型化三元组** | ❌ **明确不适用**（见 §2.5） | — |
| **H. 规则 / 句法 / 共现** | 强先验、可解释 | 结构元数据 | ⚠️ **本项目已测：无增益** | ~0 |
| **I. 分类体系 / 先修关系专门方法** | **有向** `prerequisite` | 概念对 + 结构特征 | ⚠️ 有成熟范式可借（见 §2.6） | 中 |

### 2.2 A / B：嵌入类 —— 结论是「别换模型，改几何」

**A（现状）** 的能力边界已在 §1 说清：**能召回、不能定型**。

**B（后处理）是我这次调研里最"便宜且对症"的发现。**
各向异性是公认问题，修法成熟：

- **BERT-flow**（arXiv:2011.05864）：用可逆流把嵌入分布拉向各向同性高斯，直接改善 STS。
- **Whitening**（arXiv:2103.15316）：去均值 + 去相关，**一行矩阵运算**，论文报告
  "更好的语义 + 更快的检索"。
- **All-but-the-Top**（arXiv:1702.01417）：去掉前若干主成分，简单有效。

**我在你真库上实测了白化效果**（只读，未写库）：

| 指标 | 原样 | 白化后 |
|---|---|---|
| 成对余弦 P50 | 0.4934 | **-0.0137**（居中，符合直觉） |
| 最近邻 P50 | 0.8653 | **0.7191** |
| 最近邻 ≥ 0.80 的卡占比 | **80.2%** | **33.5%** ← 阈值恢复分辨力 |
| 最近邻 ≥ 0.75 的卡占比 | 92.8% | 43.2% |

**实现代价（已实测）**：
- 需要存一个 **1024×1024 float32 白化矩阵 = 4.2 MB** + 均值向量 4.1 KB
  → **可作 BLOB 存进现有 SQLite，与向量同库同表，不违反硬约束**
- 变换全部 3469 条向量：**37 ms**（CPU，numpy）
- 全量成对矩阵：**71 ms**

> ⚠️ **诚实登记的两条风险**：
> 1. **阈值必须重新标定** —— 白化后 P90 只有 0.0303，旧的 0.75/0.80 完全失效。
> 2. **白化矩阵是语料相关的**，新卡持续入库会漂移，需要**定期重算**
>    （建议按"新增卡数 > N%"或每周重算；重算本身 < 1 s）。
> 3. **它不创造新信息**，只是把已有信息从被压缩的窄带里"摊开"。
>    对 §1.2 反例 C（父子结构只有 0.62）**大概率仍然救不回来** ——
>    那类关系的信号本来就不在相似度空间里，需要 §2.4 的 LLM 定型。

**⚠️ 一个必须先修的前置问题**：`embedding_service.py:66-83` 会按可用内存
（阈值 `config.py:142` = 4.0 GB）**自动降级** bge-m3(1024d) → bge-small-zh-v1.5(512d)。
本机实测 **总内存 15.71 GB、可用仅 2.95 GB** → **这台机器长期在降级**。
真库当前 3469 张**全是** `BAAI/bge-m3`/1024d（历史遗留），但**新入库的卡会是 512 维** ——
一旦混入，`graph_service.py:406-417` 会**丢弃少数派**（宁可少用也不混算）。
**建议**：要么把阈值降到实际可满足，要么**明确固定用 bge-small-zh-v1.5 并全量重嵌** ——
"时好时坏的模型"比"稳定的小模型"更糟。

### 2.3 C / D：有监督 RE 与 OpenIE —— 都不适用，理由不同

**C. 有监督关系抽取**（代表工作：REBEL, EMNLP Findings 2021, DOI `10.18653/v1/2021.findings-emnlp.204`；
DocRED, ACL 2019, arXiv:1906.06127）：
- 它们解决的是"**给定实体对，在句子里找到它们之间的预定义关系**"。
- 你需要的是"**在两张卡之间发现关系**"，且**没有标注数据**、**没有实体层**。
- 训练一个中文 RE 模型需要成千上万条标注三元组；你有 **604 条无类型无向边**。
- **❌ 不可行**。但它的**输出格式**（`(head, relation, tail)`）值得借用 —— 这正是
  `card_relations` 表已经有的形状。

**D. OpenIE**（如 OpenIE 5 / Stanford；综述见 arXiv:2212.09376）：
- OpenIE 从**完整句子**里抽 `(主语, 谓语, 宾语)`。
- 你的卡片 `content` **中位 40 字**，很多根本不是完整句（是术语、定义片段、公式）。
- 即使抽出来，得到的是"卡片内部的断言"，**不是"卡片之间的关系"** ——
  **粒度错配**。
- **❌ 不可行**。

### 2.4 E：LLM 成对/批量判定 —— 可行，但**必须召回前置**

**这是唯一能产出你真正想要的东西（有类型、有方向）的路径。**
先算清组合爆炸，否则一定做错：

**❌ 全量成对**：`C(3469,2) = 6,014,646` 对。
按每批 20 对估算，需 **30 万次** API 调用；本项目 `llm_max_rpm = 10`（`config.py:323`）
→ **约 500 小时**。**不可行**，且完全没必要。

**✅ 召回前置（recall-then-rerank）**：先用**便宜的**余弦（71 ms）取候选，
再让**贵的** LLM 只判候选。这是稠密检索的标准范式（DPR, arXiv:2004.04906；
ColBERT 的 late interaction, arXiv:2004.12832）。

**具体到你的规模（我算过账）**：

| 项 | 数值 |
|---|---|
| 候选对（现行规则，全量跑一遍） | **7020 条** |
| 每批 20 对（复用现有 `BATCH_SIZE`） | **351 次**调用 |
| 输入 token/次（卡片中位 53 字 + prompt） | ≈ 1.2 K |
| 输出 token/次（20 条类型+理由） | ≈ 0.4 K |
| **总计** | ≈ **42 万输入 + 14 万输出 token** |
| 按 `llm_max_rpm = 10` | **约 35 分钟**（可断点续跑） |

**这完全付得起。** 而且项目**已经有全套基础设施**：
`LLMService.infer_card_relations`、结构化校验（`llm/structured.py:47` 的
`RELATION_TYPES`）、网关记账与**缓存**（`llm/gateway.py:537` 命中缓存也记账但 `cost=0`）、
日配额（`llm_daily_token_quota` / `llm_daily_cost_quota`）。

**但现状的 B 路径有个致命缺陷必须修**（`graph_service.py:824-871`）：
取**前 100 张**卡、每 **20 张一批**、**只在批内**判关系。

```
批内对数 = 5 批 × C(20,2)=190 = 950 对
全部对数 = C(100,2) = 4,950 对        → 覆盖率 19.2%
相对全量 = C(3469,2) = 6,014,646 对   → 覆盖率 0.016%
```

**跨批次的卡片对永远不会被比较。** 正确做法是**用 A 的候选对喂给它**，
而不是让它自己在批内瞎找。

### 2.5 G：知识图谱嵌入（TransE / RotatE）—— **明确不适用**，理由有三

这是最容易被"听起来很对口"骗到的选项，所以说透：

- **TransE**（NIPS 2013, `10.1609/aaai.v28i1.8870` 为其超平面变体 TransH；
  TransE 本体见 NeurIPS 2013 proceedings）把关系建模为**平移** `h + r ≈ t`。
- **RotatE**（ICLR 2019, **arXiv:1902.10197**）把关系建模为复空间**旋转** `t = h ∘ r`，
  能表达**对称/反对称/逆/复合**四种关系模式 —— 听起来完美匹配你的需求。

**但它们的输入是"已存在的图"**：KGE 通过**在已知三元组上训练**，来预测**缺失的边**。
它们**不能**从文本里发现"这两张卡是前置关系"。

对你而言：

| 障碍 | 实测/事实 |
|---|---|
| 训练集规模 | 你有 **604 条边 / 3469 节点**，密度 ≈ **0.0001**。KGE 通常需**数万~数百万**三元组 |
| 关系类型 | 你的 604 条**全是 `related`，无一条有类型**。RotatE 的旋转**没有类型可旋转** |
| 硬件 | 需 PyTorch 训练循环；`torch 2.14.0+cpu`、`cuda False`、可用内存 2.95 GB |
| 收益 | 即使训出来，也只能复现"余弦已经找到的"共现结构 |

**❌ 结论：不适用。** 与你仓库里 `docs/graph-relation-methods.md:192` 已登记的判断一致 ——
**等边数上一个数量级、且有类型之后**再谈。

> 补充一个容易混淆的点：**"知识图谱嵌入"与"把文本嵌入"是两件事**。
> 前者嵌入**图结构**（需要边），后者嵌入**文本**（你现在做的）。
> 你缺的不是更好的嵌入，是**边**。

### 2.6 I：先修关系（prerequisite）专门方法 —— 有成熟范式可借

这是学术上**直接研究你这个需求**的分支，值得认真对待：

| 工作 | 出处 | 方法要点 |
|---|---|---|
| **Prerequisite Relation Learning for Concepts in MOOCs** | EMNLP 2017, `10.18653/v1/p17-1133` | 从**课程/教材结构**（章节顺序、引用）学先修 |
| **PREREQ / Inferring Concept Prerequisite Relations** | AAAI 2019, `10.1609/aaai.v33i01.33019589` | 用**多源特征**（共现、上下文、结构）判概念对 |
| **Concept Extraction and Prerequisite Relation Learning** | AAAI 2019, `10.1609/aaai.v33i01.33019678` | 概念抽取 + 先修联合 |
| **LectureBank / What Should I Learn First** | arXiv:1811.12181 | 数据集 + 嵌入法基线 |
| **R-VGAE**（无监督先修链） | arXiv:2004.10610 | **变分图自编码器**，无需标注 |
| **跨域无监督先修链** | arXiv:2105.03505 | 跨域迁移 |
| **多准则先修推断** | arXiv:2509.05393 | 多信号融合（**最新，与你的处境最像**） |

**可迁移的关键洞察（三条）**：

1. **结构先验极强**。这些工作普遍用到「同课程 / 同章节 / 顺序」——
   **你的数据里已经有 `note_id` 和 `chapter_title`**，而且你自己的盲判已经证明
   **"是否同笔记"是最强的分档轴**（§9.4）。**这正是先修关系文献的标准特征**。
2. **它们几乎都做"排序"而不是"阈值判定"** —— 输出是候选对的**分数排序**，
   交由下游（推荐/课程编排）消费。**这与你"待审队列"的形态天然匹配。**
3. **R-VGAE / 多准则**这类**无监督 / 弱监督**路线才适合你 ——
   因为你**没有标注**。

**❌ 但直接套用不行**：它们大多在**英文课程大纲**上做，且需要**概念（concept）粒度**
与**课程结构元数据**。你的卡片是中文技术标准条款，**没有课程先后顺序**。

**✅ 可借的是范式，不是模型**：把「多信号融合 + 排序输出 + 结构先验」拿过来，
用你的 `note_id` / `chapter_title` / 共现 / 余弦做特征。**这就是 §4 P1 的设计。**

### 2.7 F / H：图结构与规则 —— 本项目**已经实测过，没有增益**

**F. 链路预测**（共同邻居、Adamic-Adar）：
- Adamic-Adar 出自 *Friends and neighbors on the Web*, **Social Networks 24(3), 2003**,
  DOI `10.1016/S0378-8733(03)00009-1`；链路预测的系统性评估见
  Liben-Nowell & Kleinberg, *The link-prediction problem for social networks*, JASIST 2007。
- 定义：`AA(u,v) = Σ_{w ∈ N(u)∩N(v)} 1 / log|N(w)|`
- **在本场景的问题**：这类指标**在稀疏图上失效** —— 你的图密度 0.0001，
  **绝大多数孤点的共同邻居数 = 0**，指标恒等于 0，**没有区分力**。
- **⚠️ 但它可以作为"排序特征"**：等边多起来之后（P0 之后），
  共同邻居会开始有值。**当前只能当辅助特征，不能当主判据。**

**H. 规则 / 句法 / 共现**：
- **这一条你自己的项目已经测过并否决了**，值得引用：
  `docs/journal/relation-quality-2026-09-26.md` §8.3 的盲判信号对拍：

  | 信号 | 真 中位 | 假 中位 | 单阈值最优 |
  |---|---|---|---|
  | **余弦相似度** | 0.831 | 0.589 | **90%** |
  | 标题 bigram | 0.250 | 0.000 | 87% |
  | 标题+正文 bigram | 0.154 | 0.019 | 85% |
  | 标题最长公共子串 | 4 | 0 | 83% |

  结论（§8.3）：**"盲判下余弦反而是最好的单信号"**，
  **"词法闸在 0.75 下无增益（74% → 74%），因此不采纳"**。
- **⚠️ 所以：不要重复走词法/共现这条路** —— 你已经有实测否证了。
  共现可作为**排序特征**，不可作为**闸门**。

> 关于 **FTS5**：项目已有 `chunks_fts`（全文索引建在 **chunk** 上，不是 card）。
> **当前规模下不建议给 card 建 FTS5 做召回** —— 因为精确余弦全量只要 **71 ms**，
> FTS5 反而**引入召回损失**（词法匹配不到语义近邻）。**它只在语料再大一个数量级时才有价值**
> （`graph_service.py:362` 的注释已经写了同样的判断，我实测支持它）。

## 3. 问题三：80% 孤立节点的病因诊断

你要求分清四种可能。我的判断**有明确的主次**：

| 可能病因 | 判定 | 证据 |
|---|---|---|
| **召回问题**（候选对根本没被比较） | ✅ **主因（决定性）** | **F1/F2**：2683/3028 孤点的最近邻**已过阈值**；全量跑一遍覆盖 **88.6%**，只要 **725 ms**。而 `MAX_CARDS_FOR_SUGGEST = 200`（`graph_service.py:108`）把每次调用限制在 200 张候选 → **要跑 ~15 次才覆盖一轮**，而真库里 `suggested` 边为 **0**（从未触发） |
| **判定方法问题**（方法太弱） | ⚠️ **次要，但真实** | 方法**只能产出无向 `related`**。真库 **604 条边 100% 是 `related`**，`prerequisite`/`subsequent`/`contrast` **零使用**。你要的"关系"它表达不了 —— 但这不是 80% 孤立的成因 |
| **阈值/参数问题** | ❌ **不是** | 604 条 `confirmed` 边的分数区间 `[0.7501, 0.9869]` 与 `MIN_SIMILARITY = 0.75` 吻合，且**用户全认了**。降阈值只会引入噪声（盲判 v2：`0.65-0.70` 层可导航率仅 21%） |
| **数据本身问题**（卡太短、太同质） | ⚠️ **背景条件，非主因** | content 中位 **40 字**、嵌入文本中位 **53 字**；各向异性 `\|mean\|=0.70`。它**削弱判据上限**（§1.3/§1.4），但**不解释**"2683 张本该连上的没连上" |

### 3.1 为什么"召回"是主因 —— 一个决定性的数量关系

```
孤点 3028 张，其中 2683 张（88.6%）的最近邻已过现行阈值
→ 这些边"判据认为该建"，但一条都没建
→ 唯一解释：它们从未被放进候选池

MAX_CARDS_FOR_SUGGEST = 200  →  3028 / 200 ≈ 15 轮
真库 suggested 关系 = 0      →  一轮都没跑过
```

**"判据找不到"与"判据没机会找"是两件事。** 你遇到的是后者。

### 3.2 但**不要**因此认为"方法没问题"

两件事必须同时说清：

1. **修召回能立刻解决 80% 孤立**（88.6% 的孤点能连上）—— 这是 P0，一天之内可验证。
2. **修召回不会给你"关系"**，只给你**更多的 `related`**。
   而 `related` 恰恰是用户**看不出价值**的那种边（"这两张卡有关系"——
   用户自己也知道，他要的是**怎么个关系法**）。

> 仓库里 `docs/overhaul-plan.md:865` 已经登记了这个判断：
> **"盲判显示约 20% 的真关系有明确类型，所以这一块值得做"** —— 我认同。
> 换句话说：**边的数量问题靠 P0，边的价值问题靠 P2。**

## 5. 明确推荐：如果只能做一件事

> ## 做 P0-1：把 `MAX_CARDS_FOR_SUGGEST` 从 200 放开到全量
> ## **并且必须同时做 P0-2（排序 + 分批展示）** —— 否则等于没做

**为什么是它，而不是"换个更好的判据"：**

1. **它是唯一能把 88.6% 的孤点一次性救回来的改动。**
   实测：**2683/3028** 孤点的最近邻**已经过现行阈值** ——
   这些边判据**早就想建**，只是**从来没轮到它们**。
2. **代价小到可以忽略：0.7 秒 CPU、0 字节存储增量。**
   向量已在 SQLite 里（`graph_service.py:364-378` 已经改成从库读）。
   连模型都不用加载 —— 因此**完全不触碰 2.6~4 GB 内存红线**。
3. **它是唯一"一天内可验证"的改动。** 改一个常量，在真库副本上跑一遍生产函数，
   四个数（新建边 / 覆盖孤点 / 耗时 / 队列长度）立刻见分晓。
   **P1/P2 的所有方案都需要先有这批边才有意义** ——
   P1-2 的 Adamic-Adar 在稀疏图上是恒 0 的，P2 的 LLM 定型需要候选对。
   **P0 是其他一切的前置条件。**
4. **它不推翻任何既定决策**：不动数据库、不引入中间件、不动产品语义、
   不加依赖 —— 完全在 AGENTS.md §2 的禁区之外。

**为什么必须捆绑 P0-2：**
一次产出 7020 条 `suggested` 而用户面对一个 7020 条的待审列表，
**产品体验比现在更糟**（现在至少是"图很稀"，之后是"审核队列不可用"）。
仓库里 `docs/graph-relation-methods.md:168` 已经预警过这一点，我实测确认了量级。

**做完 P0 之后紧接着做 P1-1（白化）**，因为它是**第二便宜且对症**的：
4.2 MB、37 ms，把"阈值"这个已经失效的旋钮修回可用 ——
而阈值失效（`|mean|=0.70`、80.2% 的卡最近邻 ≥0.80）正是你**下一阶段**
做排序和定型时的最大障碍。

**最后，诚实说明这个推荐不解决什么：**
P0 只会让图谱**变密**，不会让它**变得有信息量** ——
产出仍然是清一色 `related`。**你原话里"方法比较简单"的那层不满，
要等 P2-1 才真正解决。** 但 P0 是 P2 的入场券：
没有候选对，LLM 无从下手；有了候选对，35 分钟、42 万 token 就能换来
一张**有类型、有方向**的知识图谱。
