### ① 卡片页真分页（`389a4ba`）

- **改了什么**：`PAGE_SIZE = 100` + 页码 state；分页控件与 `NotesList.tsx:422-456` 同形；
  页尾「本页显示第 X–Y 张，共 N 张」；页码越界守卫；搜索时回第 1 页。
- **为什么不是把 999 改成 9999**：后端上限确实是 9999（`api/understanding.py:363`），
  但那样 DOM 会同时挂 3469 张卡 —— 走查实测 999 张时已有 3441 个按钮 / 161,766 字。
- **已知取舍**：分页在卡片粒度、分组在笔记粒度 ⇒ 同篇笔记的卡片可能跨页。
  写在 `PAGE_SIZE` 的注释里，没藏。
- **验证**：新增 3 条用例（请求带 100 与当前页码 / 翻页 / 只有一页时不显示控件），
  6 passed；tsc + eslint + build 全过。

### ② `daily-plan` 按 `error_code` 分流（`8e353de`）

- **症状**：`Dashboard.tsx` 用 `msg.includes('active goals')` 匹配**英文文案**判断
  "这个 400 是不是正常业务状态"。后端改一个字就静默失效，而失效的样子是
  "控制台红字又回来了"，不是报错（overhaul-plan F-19 的形态）。
- **改法**：新增 `errorCodeOf(e)`（与 `Review.tsx:41-45` 逐字同形），
  分流依据改成 `errorCodeOf(e) !== 'GOAL_NONE_ACTIVE'`。
- **顺带核过全仓**：`message.includes` 的**活代码**只剩这一处，其余命中都在注释里。
- **刻意没做**：**没有**把后端改成"无目标返回 200 + 空计划"。那会改
  `DailyPlanResponse` 的契约形状（`id`/`goal_id`/`plan_date` 都是必填），
  要动 schemas + openapi.json + 前端类型 + 生成物，买到的只是"少一条 400 日志" ——
  而正确性已经由 `error_code` 分流拿到了。要做是独立一轮。
- **验证**：新增 `Dashboard.test.tsx`（此前这一页**没有**测试文件），3 条含**反空转**
  （其它错误码仍要报失败、连 code 都没有的异常也按失败计）。
- **一处如实记录**：`core/error_messages.py:396-399` 记着 `GOAL_NONE_ACTIVE` 的
  zh-CN 值**本来就是那句英文**，并说明"改中文界面的文案属于产品决策"。
  **本次没有动它** —— 改的是分流依据，不是文案。

### ④ 去掉 `error_code` 前缀（`1c3db64`）

- **症状**：`request()` 抛的是 `` `${code}: ${detail}` ``，用户看到
  `NOTE_EXPORT_EMPTY: 笔记没有可导出的正文`。
- **改法**：`throw new ApiError(detail, code)` —— **`code` 字段照旧带上**，
  所以全仓按 code 分流的地方一行都不用改。至此三处 `ApiError.message` 拼法统一
  （`downloadRequest` / `askQuestionStream` 本来就是只给 detail）。
- **为什么不违反阶段 0.11 的"刻意保留兼容口径"**：那条口径把机器码留在了用户看得见
  的地方，而本仓库的判据是"代码实测 > 文档"。两处旧注释（`ApiError` 的
  「为什么 message 的构造一个字都没改」、`readErrorBody` 的「三处拼法仍然不同」）
  **就地改成新口径**，不留一句与代码矛盾的话。
- **验证**：新增 1 条用例同时钉两半（文案干净 + `code` 仍可读）。
