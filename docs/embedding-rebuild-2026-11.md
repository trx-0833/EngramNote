# 嵌入向量重建记录（2026-11-15）

> 起因：`/qa` 问「拉哇水电站水导轴承有几块？」答“没有找到”，但库里确实有内容。
> 排查与处置记录在此，供以后重装/换机时对照。

## 1. 现象与取证

| 事实 | 取证方式 |
| --- | --- |
| 内容确实在库里 | `chunks` 里 6 条含“水导轴承”，分属《水轮发电机组…》等笔记 |
| 检索返回 5 条，**上下文里没有“水导轴承”** | 直接调 `RAGService.retrieve_context()`，打印 `context` |
| 日志：`向量检索跳过 608 条维度不符的 chunk` | 同上 |

## 2. 根因

`chunks.embedding` 混着两种维度：

```
BAAI/bge-m3            1024 维  608 条
BAAI/bge-small-zh-v1.5  512 维  289 条
```

**为什么会有两种**：嵌入模型在**内存不足时自动降级**——

```
可用内存不足（3.2GB < 4.0GB），跳过主模型 BAAI/bge-m3，改用降级模型 BAAI/bge-small-zh-v1.5
```

于是同一台机器不同时刻写入的向量维度不同；检索时按其中一种维度算，另一种**整批跳过**。
含“水导轴承”的 6 条恰好全在 1024 那批里，而检索侧降级到 512 ⇒ 它们永远进不了候选。

这不是“换过模型留下的残留”，而是**同一配置在不同内存条件下产出不同维度**。

## 3. 处置（2026-11-15，已获用户批准）

1. 清空全部 `chunks` 向量（`embedding=NULL, embedding_model=NULL, has_embedding=0`），897 条；
2. 用降级模型（bge-small-zh，512 维）分三轮回填：400 + 400 + 97，`failed=0`；
3. 结果：**897 条全部 512 维、待补 0**。

⚠️ 踩到的坑：`_pending_counts()` 判“待补”看的是 `has_embedding` 列，**不是**
`embedding IS NULL`。只清 `embedding` 会让回填任务认为无事可做（`skipped: True`）——
两个字段必须一起重置。

## 4. 效果

同一问题：

- 改前：上下文**不含**“水导轴承”，只有两篇笔记的“1 范围”开头；
- 改后：上下文**含**“水导轴承”（命中 4.1.1“技术供水系统为上导轴承冷却器…水导轴承冷却器…”）。

但这只是“能检到”，不等于“答得准”：top-1 仍是该笔记的开头块，而用户要的是
“水导轴承有几块（几块瓦）”。当前内存下只能用 512 维模型，语义排序能力有限。

## 5. 后续建议（按性价比）

1. **提高 `top_k`**（5 → 8~10）：让更多候选进上下文，包含“瓦/块”那类段落。代价是上下文变长，需同步看预算；
2. **让关键词通道的强命中优先**：FTS5 命中“水导轴承”的块应保证进候选，不被向量开头块挤掉；
3. **加内存后重跑 bge-m3**：`4GB` 是硬门槛（当前 3.2GB 可用）。换机或扩容后按本文 §3 重做一遍即可切回 1024 维；两种维度**不能混存**。
