## 1. 怎么跑

```bash
cd frontend
npm run a11y            # = playwright test --project=a11y（该 project 固定 --workers=4）
npm run a11y:headed     # 带界面调试（单 worker）
npm run e2e             # 功能层（10 条），**不含**审计
npm run e2e:all         # 两个 project 一起跑（25 条），约 40 秒
```

一条命令自洽：dev server 由 `playwright.config.ts` 的 `webServer` 自动拉起与关闭
（端口 **4319**、`--strictPort`），与 `npm run e2e` 完全同一套机制 —— 不需要先开服务，
也不会碰人类手上 DSH Web GUI 的 3080。

### 两个 project，不是"一个 project 里的两个文件"

`playwright.config.ts` 里现在有**两个 project**：

| project | `testMatch` | 用例数 | worker | 谁在跑 |
|---|---|---|---|---|
| `chromium` | `**/!(*a11y).spec.ts` | 10 | 默认（按核数） | `npm run e2e` |
| `a11y` | `**/a11y.spec.ts` | **15** | **4**（写死在 project 里） | `npm run a11y` |

**为什么必须分开**（两个都是实测踩出来的）：

1. **并发**：8 个 worker 同时打 Vite dev server 时，**按需转换**（页面都是
   `React.lazy` 懒加载，每个路由第一次访问才现场编译）会把首屏拖到 10 秒以上，
   于是"等欢迎标题出现"超时 —— 失败信息指向"页面没渲染"，真实原因是
   "开发服务器被 8 个 axe 注入 + 懒加载请求同时敲"。审计要的是**页面内容**，
   不是吞吐。定到 4 之后稳定在 ~21 秒（覆盖轮后 15 条用例约 **31 秒**）。
2. **`testMatch` 是交集**：`playwright test a11y.spec.ts` 这种"命令行传文件名"
   会与顶层 `testMatch`（已排除 a11y）取交集，直接得到 `No tests found`。
   用 project 表达"这一组用例有自己的匹配式与参数"才是配置该说的话 ——
   这个坑在接线时真踩到了一次，写在这里免得下次再踩。

| 项 | 值 |
|---|---|
| 引擎 | `@axe-core/playwright` **4.13.0**（devDependency，连带 `axe-core` 4.13.0） |
| 规则集 | `wcag2a`、`wcag2aa`、`wcag21a`、`wcag21aa`、`best-practice` |
| 浏览器 | 仍是那一个 Chromium（`npm run e2e` 用的同一个，没有额外下载） |
| 用例 | **25 条**：23 条扫描用例（合计覆盖 **25 个场景** —— 登录页含 2 个状态、卡片复习含 2 个状态）+ 2 条自检 |
| 实测耗时 | 约 **42 秒**（本机，热缓存；15 个用例时是 31 秒，涨的全是新场景） |

**应用不是"无障碍合格"的**：axe 的 WCAG 2.0/2.1 A+AA 规则集在 9 个真实界面上
报出了 30 组"规则 × 场景"违规，其中 2 个节点是 `critical`（表单控件没有可访问名）、

## 3. 发现（按优先级排序，含逐条判定）

**判定口径：**
- **(a) 真实问题** —— 会影响真实用户的某种输入方式（键盘 / 屏幕阅读器 / 低视力），
  且修法明确；
- **(b) 需要人工确认 / 可能是设计取舍** —— 规则的判据与产品意图有张力，
  或依赖用户内容，需要人做决定；
- **(c) 真实但在本轮范围外** —— 确实是问题，但归属别的工作流（如设计令牌由 5.6 管）。

`id` 与 `frontend/e2e/a11y.spec.ts` 里的 `REGISTRY` **一一对应** ——
测试里每一条豁免都能在这里查到为什么。

**读法（修复轮之后）**：下面每张表都多了一列「修复」。
`✅ 已修` = 该规则的节点数已归零，登记项已**删除**，回归会被判成"未登记"而失败；
`⬜ 待人工决定` = 仍留在登记表里、上限已下调到实测值。
**已修的条目一律不删行** —— 删了就没人知道当初是什么问题、为什么那样修。

#### F-11 的两个附加项（都是 axe 报不出来的）

原实现把外观整块写在 tsx 的 `style={{...}}` 里，其中包括 `outline: 'none'`。
**内联样式的权重高于任何选择器** —— 只要它还留在 tsx 里，样式表里的
`:focus-visible` 焦点环就永远不会生效。所以外观整体搬进了新的
`src/pages/notedetail/NoteDetailHeader.module.css`，随数据变化的那一项
（角色对应的底色）由 CSS 自定义属性 `--note-role-bg` 传入。

1. **焦点可见**（axe 不检查，见 §4.1）：`:focus-visible` 给两层环 ——
   2px 白色内圈（对两种底色分别 4.78:1 / 7.10:1）+ 2px 墨色外圈
   （`--color-primary-hover`，白底 15.89:1）。用 `box-shadow` 而不是
   `outline` + `outline-offset`：这一行元信息是 `align-items:center` 的 flex，
   画到控件外面的那两圈会被相邻兄弟压住；`box-shadow` 也不改变控件几何。
   **实测**（真 Chromium，聚焦后 `getComputedStyle`）：
   `box-shadow: rgb(255,255,255) 0 0 0 2px, rgb(22,33,62) 0 0 0 4px`。
2. **下拉框自身的对比度**（`F-12` 的第三种成因，axe 报了）：
   白字压在原底色上只有 3.68:1。`material` 由 `#3b82f6` 压深到 **`#316fd8`**
   （白底白字 **4.78:1**）；`personal_note` 由 `#8b5cf6` 压深到 **`#6d28d9`**
   （**7.10:1**）。色相不变，只是深一档。

## 4. axe **看不见**的东西（这一层明确做不到的事）

下面每一条都是**当前没有任何一层在守**的。写在这里不是免责，是待办清单。

> **修复轮补进去的两条**（都只是"修了具体那一处"，**没有**变成自动门禁）：
> 笔记角色下拉框的焦点环（§4.1）与 `.sidebar-collapse-btn` 的对比度（§4.3）。
> 两条后面都写了实测值 —— 换句话说，"人工看一眼"确实能结案，
> 但**下一次改动不会有人替你再看一遍**，这些清单项不会自己变绿。

### 4.1 焦点顺序、焦点可见性、键盘陷阱

axe 只看 DOM 与计算样式，**不模拟 Tab 键**。所以：

- **Tab 顺序是否合理**没有验证。已登录外壳里侧边栏在 DOM 中先于 `main`
  （`App.tsx:91` 的 `<Sidebar/>` 在 `<main>` 之前），所以每个页面都要先 Tab 过
  15 个导航项才能到内容 —— 这可能是问题，也可能是有意，**本轮没有量过**。
- **焦点陷阱**（尤其在移动端抽屉与模态框里）没有验证：`LinkManagerModal`、
  `DeleteNoteDialog`、侧边栏抽屉打开时焦点会不会跑到背后？没有测。
- **`outline: none`** 出现在至少两处内联样式里（`NoteDetailHeader.tsx` 的
  `<select>`、`CardReview.tsx:129` 的容器）。前者是**真控件**，去掉焦点环
  意味着键盘用户看不出焦点在哪。axe 不检查这个（它不属于任何 ARIA 规则）。
  > **修复轮**：`NoteDetailHeader` 那处**已修** —— 外观整块搬进
  > `NoteDetailHeader.module.css`，`:focus-visible` 给"白内圈 + 墨色外圈"
  > 两层环（理由与实测值见 §3 的「F-11 的两个附加项」）。
  > 顺带把图谱过滤器 `.graph-filter-select:focus` 也补成两层环。
  > `CardReview.tsx:129` 的容器是 `tabIndex={-1}` 的**非交互**容器
  > （只用来接键盘事件），它不需要焦点环，**保持原样**。
  > **"焦点环画出来长什么样"仍然没有断言**：本次是在真 Chromium 里
  > 读 `getComputedStyle` 人工核对（`box-shadow` 两层的颜色与半径），
  > 不是自动门禁 —— 下面「后续」那条依然成立。
- **`CardReview` 的键盘约定**：该页没有输入控件，靠容器 `tabIndex={-1}` +
  `useReviewKeyboard` 接 Enter（`CardReview.tsx:71-76` 有说明）。它在 Vitest 里
  有单测，但"真浏览器里焦点落到 body 后回车还灵不灵"**没有被本层验证**。

**后续**：写几何 + `page.keyboard.press('Tab')` 的断言（记录 `document.activeElement`
序列），或引入 `@axe-core/playwright` 之外的手工脚本。这是一件**独立**的活，
不要指望 axe 顺手覆盖。

### 4.2 屏幕阅读器语义

- **可访问名算不算"好名字"**：axe 只判"有没有名字"。例如图谱过滤器加了
  `aria-label="按卡片类型筛选"` 就算过，但这个名字在实际朗读里是否清楚，
  只有人戴耳机听一遍才知道。
- **朗读顺序 / 冗余**：侧边栏 15 个按钮每个前面带 emoji（`☘ 今日学习`、
  `◎ 知识图谱`）。emoji 会不会被念成"四叶草"？axe 不管。
- **动态区域**：`Toast`、`ReviewProgress` 的进度更新、`CardReview` 的
  "下次复习: 21 天后" —— 这些**异步出现**的内容有没有 `aria-live`，
  应该念还是不该念，axe 判不了（`aria-live` 存在性它可以判，**该不该有**不行）。

### 4.3 动态状态与渐变背景上的对比度（**149 个"需人工确认"节点**）

axe 的 `color-contrast` 在**算不出背景色**时不会猜，而是把节点丢进 `incomplete`。
本项目里这是最大的一类（跨场景相加 149 个节点，比违规节点还多一倍），成因有两类：

1. **渐变文字**：`background-clip: text` + `-webkit-text-fill-color: transparent`
   （`layout.css:26/90-93` 的 `.sidebar-logo`、`components.css:270-281` 的
   `.gradient-text` / `.gradient-text-gold`）。**文字的前景色是透明的**，
   axe 拿不到；要人工按渐变两端色分别算对比度。
   命中的有：侧边栏 logo「EngramNote」、仪表盘 h1、知识图谱 h1 等。
2. **半透明/图标型控件**：`.sidebar-collapse-btn`（28×28，`layout.css:110-123`，
   `color: var(--color-text-tertiary)`）、`.sidebar-item-icon` 等。
   它们多半带有 `opacity` 或叠加在非纯色上。

**最值得先看的一条**：`.sidebar-collapse-btn` 用的是 `--color-text-tertiary`
（#9a9ab0）—— 与 F-04 同色。若其背景确实是白色，它就是 **2.75:1**，
即又一个真实违规，只是 axe 没能确定背景而没报出来。

> **修复轮的实测答复**：这条猜对了成因、猜对了色值，**结论已经被修掉**。
> 在真 Chromium 里取计算样式：`.sidebar-collapse-btn` 的
> `color: rgb(111,111,138)`（= 新的 `--color-text-tertiary`），背景是侧边栏的
> `#ffffff`（它自己是 `background: transparent`）→ **4.86:1，达标**。
> 也就是说：这一条**不是"axe 看不见所以永远算不清"**，
> 花一次 `getComputedStyle` 就结案了 —— 值得推广给同类节点。
> ⚠️ 仍然没结案的是**渐变文字**那一类（`.sidebar-logo`、`.gradient-text`、
> 仪表盘 h1、知识图谱 h1）：它们的前景色是 `transparent`，取计算样式也拿不到
> "看起来是什么颜色"，必须按渐变两端色分别算，**本轮没有做**。
> 那 149 个 `incomplete` 节点里还剩多少这类，见每次运行的 JSON 附件。

**后续**：人工对照 `docs/design` 或直接在浏览器里取色算比值；
或引入能处理渐变的对比度工具。**不要**因为 axe 没报就当它没问题。

#### 4.3.1 axe **结构上**不下结论的第二种情况：单字符文本（覆盖轮新增）

上面那类是"背景算不出来"。覆盖轮在今日学习页撞到了**另一类**，读 axe-core 源码才看明白
（`node_modules/axe-core/axe.js` 的 `colorContrastEvaluate`，约 27277 行）：

```js
var shortTextContent = visibleText.length === 1;
...
} else if (!isValid && shortTextContent && !ignoreLength) {
  missing = 'shortTextContent';
}
...
if (fgColor === null || bgColor === null || equalRatio || shortTextContent && !ignoreLength && !isValid) {
  return void 0;   // → incomplete，而不是 violation
}
```

也就是说：**文本只有一个字符、且对比度不足时，axe 返回"不下结论"** ——
节点进 `incomplete`，永远**不会**变成违规。

今日学习页的三个**优先级徽章**（「高 / 中 / 低」正好各一个字）正是这种情况。
本轮把它们量了出来（真 Chromium，`getComputedStyle` + 逐层合成背景）：

| 徽章 | 前景 | 背景 | 实测比值 | 字号/字重 | 要求 | 结论 |
|---|---|---|---|---|---|---|
| 高（priority 1） | `rgb(255,255,255)` | `rgb(244,67,54)` | **3.68:1** | 11.2px / 400 | 4.5:1 | 不足 |
| 中（priority 2） | `rgb(255,255,255)` | `rgb(255,152,0)` | **2.16:1** | 11.2px / 400 | 4.5:1 | 不足 |
| 低（priority 3） | `rgb(255,255,255)` | `rgb(16,185,129)` | **2.54:1** | 11.2px / 400 | 4.5:1 | 不足 |

**这三条没有任何门禁**（axe 报不出来），数字随每次运行存进
`a11y-today-learn-badges.json` 附件。⇒ 记为 **F-36（实测，无门禁）**，
下一轮修色值时**同时**补一条基于 `measureContrast` 的断言，否则修完也没人守着。

> 这条经验可以推广：**凡是"一个字/一个字符"的状态徽章、角标、计数气泡，
> 都不要指望 axe 的 `color-contrast`** —— 它们会被静默归入"需人工确认"。

### 4.4 移动端触控目标尺寸

`dashboard-mobile` 场景（375×667）**0 条触控尺寸类违规** —— 不是因为尺寸没问题，
而是因为 **axe-core 4.13 根本没有这条规则**（WCAG 2.5.8 Target Size 是 AA，
但 axe 不实现几何判定）。这条用例里已把这一点写成断言
（`expect(touchRules).toEqual([])` —— 钉住的是"工具没有这个能力"这个事实），

已知的具体疑点（手工看代码就能确认的）：
- `.sidebar-collapse-btn` **28×28 px**（`layout.css:114-115`）—— 低于常见的
  44×44 建议值，也低于 WCAG 2.5.8 的 24×24 下限之外更严的门槛；
- `SelfRatingButtons` 的四个档位在窄屏下是否够大（`SelfRatingButtons.module.css`

- 侧边栏导航项高度、笔记卡片上的删除按钮（`icon-btn` 一类）。

**后续**：写几何断言（`boundingBox()` 的宽高 ≥ 阈值），而不是等 axe。
这是本层**结构上**做不到的事。

## 6. 测试怎么判定"通过"（以及为什么不许空过）

### 判定尺度：登记表 + 上限

`e2e/a11y.spec.ts` 里的 `REGISTRY` 把当前**已知的每条违规**逐条写下来
（`id` + 规则 + 场景 + 影响等级 + 节点数 + 归属）。运行时：

1. 出现**未登记**的规则 → **失败**（这是真正在守的部分：新回归立刻红）；
2. 已登记规则的**节点数超过**登记上限 → **失败**（影响面扩大）；
3. 已登记规则的**影响等级高于**登记值 → **失败**（变严重）；
4. 同一（场景，规则）出现两条登记项 → **失败**（那种写法会让匹配悄悄失效）；
5. 登记表里有**没写归属**的条目 → **失败**（没有归属的豁免就是"忘了修"）。

**外加一条不是"登记表"的门禁**（清债轮加的，见 §10.7）：
axe 对"只有一个字符"的文本**按设计不下结论**（F-36），所以那三个优先级徽章
既没有 violation 也没有可登记的条目 —— 唯一守得住它们的是
`today-learn` 用例里那条基于 `measureContrast` 的**阈值断言**
（`m.ratio >= m.required`，即 ≥4.5:1，不是"等于某个当前值"）。

**为什么只卡上限、不要求精确相等**：本文件是给修 bug 的人看的。若要求相等，
他每修掉一条就得同时改测试里的数字，很快就会出现"顺手把数字改大一点"，
门禁随即失效。只卡上限意味着**修好立刻生效、不需要改测试文件**；
而问题变多一定失败。代价是它**不会告诉你"某条已被修好"** ——
那件事由上面 §3 的表格（人工过一遍）负责。

### 防线：不许空过

一个坏掉的选择器、一次失败的懒加载、一个被桩吃掉的接口，都会让页面渲染成空白
—— 而**空白页面的 axe 结果恒为"0 违规"**。那种绿灯比红灯更糟。因此每次扫描都断言：

- 该页**独有**的渲染标记先出现（例如笔记列表要等到"共 2 条"**和**一条笔记标题都在，
  而不是只等一个标题 —— 空态也有标题）；
- DOM 元素数 ≥ 场景下限（实测值留 ~30% 余量）；
- axe 真的执行了（`passes > 0`、评估规则数 > 20）；
- 桩没有出现"未定义响应"的接口（`/api` 桩对未知路径回 **501** 并记录，
  因为页面普遍用 `.catch(() => null)` 把它吞掉）；
- 页面无未捕获异常（`pageerror`）。

另外两条**自检用例**：

1. **注入一个没有 `alt` 的 `<img>`，断言 axe 报出 `image-alt`** ——
   守的是"扫描链路本身还活着"；
2. **登记表自检**：场景名拼写正确（写错的后果是豁免永远匹配不到，
   而维护者会去加第二条豁免，越加越乱）、（场景，规则）唯一、每条都写了归属。

### 已知的稳定性注意点

- 并发由 project 固定为 4（见 §1）。8 worker 时 Vite 的按需转换会让首屏超 10 秒，
  表现为"页面没渲染出来"，与真实原因无关；
- 端口 4319 若被上一次异常退出的 dev server 占着，`--strictPort` 会**直接失败**
  （这是有意的：悄悄换端口会让 `webServer.url` 的健康检查探一个空地址）。
  遇到时先确认没有遗留进程，而不是改成 `reuseExistingServer: true`；
- **对比度节点数会随内容漂移**：`color-contrast` 的命中数取决于"页面上有几条
  状态徽章"，桩数据一变就可能多一个节点。登记表刻意留了一点余量（上限），
  但**如果它开始因无关的数据改动而红，正确的做法是把桩数据固定住，
  而不是把上限调大**。
  > **修复轮之后这条暂时用不上了**：`color-contrast` 在 9 个场景里
  > 一个节点都不剩，登记项已全部删除 —— 现在任何一条对比度违规（哪怕 1 个节点）
  > 都会以"未登记"失败。也就是说**漂移的容忍度从"有上限"变成了 0**。
  > 这是有意的：真要再出现，先看是页面真的退化了还是桩数据变了，
  > 两种都不该用"加上限"解决。
  > **清债轮之后的状态（三句话）**：
  > ① **10 个旧场景仍然是零容忍** —— 一条对比度违规都没有因为它们没变而被放宽；
  > ② 4 个新场景的 `color-contrast` 登记项（F-28/F-29/F-33/F-35）**全部修掉、
  >    登记项全部删除** —— 现在**任何一个场景**的 `color-contrast` 只要出现
  >    1 个节点就是"未登记"失败；
  > ③ 又加了 10 个新场景（§10.2），它们的 `color-contrast` 也是 **0 节点**
  >    （五张颜色表在 F-33 那一次里已经全部过一次，见 §10.1）。
- **`minNodes` 的下限来自实测值**：新场景的下限写在各自的注释里（实测值留 ~30% 余量）。
  ⚠️ 10 个旧场景注释里的实测值（48 / 143 / 208 / 158 …）是**修复轮之前**那一版
  （与 §2 的历史表逐字相同），修复轮改了 DOM（补 `<main>`、补 `<h1>`）之后没刷新过；
  **清债轮**又补了 `<main>`（注册页）与几处标题级别，实测值再动一点
  （51 / 148 / 212 / 162 …）。**下限一直没动、也一直成立**（差值全都 ≥ 20%），
  因为下限本来就留了三成余量 —— 这正是当初不写死实测值的理由。
  新的 10 个场景的实测值与下限逐条列在 §10.2 与 §10.8。
- **端口现在可配**：`E2E_PORT=4321 npm run e2e`（默认 4319；**3080 被显式禁止**，
  写错会当场抛错）。两个 agent 同时跑 Playwright 时用这个换端口，
  而不是把"端口被占"当成测试失败。

### 排查用的一手线索

`e2e/a11y-fixtures.ts` 里的桩会把**每个 `/api` 请求**记进 `A11yStubLog.served`，
并把浏览器控制台的 error/warning 记进 `consoleErrors`。要逐条打到测试输出，
把该文件里的 `const TRACE = false` 改成 `true` 再跑一次即可
（不做成环境变量：`tsconfig.json` 的 `include` 含 `e2e` 而 `lib` 里没有
`@types/node`，写 `process.env` 会让 `npm run build` 报 TS2580）。

这套线索真的用上过一次：8 worker 并发时"页面卡在加载中"，
`served` 立刻显示**所有接口都回了 200**，于是问题被定位到开发服务器吞吐，
而不是接口或前端代码。

## 7. 与 CI 的关系

`.github/workflows/ci.yml` 的 `frontend` job 里，在 `npm run e2e` **之后**加了一步
（**只加了一步，没有改动任何现有 job 的结构**）：

```yaml
- name: Playwright a11y audit (axe-core, advisory)
  continue-on-error: true
  timeout-minutes: 10
  run: npm run a11y
```

> 同一份改动还让 `npm run e2e` 变成 `playwright test --project=chromium`
> （= 功能层 10 条，**不含**审计）—— 这是"审计单独一个 project"的必要配套：
> 不加 `--project` 时 Playwright 会把两个 project 都跑（共 25 条，
> 只是想跑功能层的人不该被塞进 15 条审计）。想两者一起跑用 `npm run e2e:all`。

**为什么是建议性（advisory）而不是阻断性：**

1. 审计当场发现了一批真实违规，修复属于后续的 5.9 修复轮。现在设成阻断，
   CI 会**长期常红**，而常红的门禁只有一个结局：被人加 `|| true` 或删掉 ——
   那比没有门禁更糟，因为它制造"我们已经在管无障碍了"的假象
   （这与本仓库 `security-scan` job 的取舍是同一个理由）。
2. `frontend/src/**` 正在被并行的 CSS 迁移改动。审计对**对比度**与**类名**敏感，
   迁移期间更容易因无关改动变红，而那种红的指向不是"这次提交引入了缺陷"。

**它仍然是有信号的一步**（不是 `|| true` 那种装饰）：审计本身会把未登记的违规
判为失败，所以这一步在 CI 日志里会明确显示"当前是否有**新**的无障碍回归"。
`continue-on-error` 只影响"是否让整个 job 变红"，不影响它跑、也不影响它报。

**升级成阻断的前置条件**（写在这里避免"以后再说"）：

1. 5.9 修复轮把 `REGISTRY` 清空或降到可接受集合；
2. `frontend/src/**` 的 CSS 迁移结束。

两条都满足后，把那一行 `continue-on-error: true` 删掉即可 —— 门槛本身已经在
测试里了，不需要另写脚本。

> **修复轮之后的进度**：第 1 条的"降到可接受集合"已经完成 ——
> `REGISTRY` 从 **30 条 / 68 个节点降到 4 条 / 4 个节点**，且剩下的 4 个节点
> 全部是同一个 **(b) 待人工决定**的问题（标题层级）。第 2 条（CSS 迁移）
> 不属于本工作流，**所以 CI 这一步现在仍然是 advisory** —— 改它需要同时
> 确认迁移状态，那是另一个 agent 的范围。
>
> **清债轮之后的进度（本轮）**：`REGISTRY` 从 **12 条 / 15 个节点降到
> 5 条 / 5 个节点** —— 上一轮那 8 条债里 **7 条的登记项已删除**
> （F-28/F-29/F-30/F-32/F-33/F-34/F-35），只剩 F-31 交回人工决定；
> 同时把最后 10 个页面接成场景（§10），新场景**一条登记项都没加**。
> **第 1 条前置条件（"清空或降到可接受集合"）现在是"5 条，且全部是同一个
> 待人工决定的问题"** —— 也就是说它卡在**人的决定**上，不再卡在工程量上。
> 第 2 条（CSS 迁移）**仍在进行中**（同一 workspace 里有并行的迁移 agent，
> 本轮改动与它交错进行），所以 CI 这一步**保持 advisory**，本轮刻意**没有**
> 碰 `.github/**`。

### 8.4 本轮踩到的两个坑（都值得记住）

1. **补 h1 会立刻引出 `heading-order`。** F-18（笔记列表缺 h1）与

### 10.4 `CardDetail` 扫不了的**真实原因**：桩的路径写错了，不是形状不对

上一轮 §5 第 3 条写的是"桩里 `/api/cards/{id}` 返回的是列表形状，加进去只会得到
加载失败页"，因此把这一页列为"先补桩才能加"。本轮实测查清：

- 应用请求的是 **`/api/understanding/cards/{cardId}`**（`api/qa.ts:186`），
  从来不是 `/api/cards/...`；
- 桩里那条 `'/api/cards': { items: [], ... }` 是一条**永远匹配不到的键**
  —— "看起来有桩"，实际请求落到 501 上，页面于是渲染成加载失败页；
- 而"列表形状"这个解释**站不住**：`CardDetail` 对响应体没有任何逐字段校验
  （`if (error || !card)`），任何**对象**（包括列表形状）都能通过那道门，
  只会渲染成空白字段。也就是说当时的结论**把一个"路径错"误读成了"形状错"**。

修法：把死键删掉，补上正确的两个路径（列表 + 详情），详情页正常渲染
（`card-detail` 场景 0 违规）。这条也解释了为什么"路径写错"比"形状写错"更隐蔽：
它不产生任何**页面内的**线索，只在 501 的桩日志里留一行（而 `log.unmatched`
断言恰好会把它抓出来 —— 前提是**它已经是一个场景**）。

### 10.5 ★ 一个从来没有任何一层发现过的**功能缺陷**（QA 页每次提问都失败）

把 `qa` 接成场景时，第一次**真的**在浏览器里问了一次，页面当场报：

```
Failed to execute 'getReader' on 'ReadableStream':
ReadableStreamDefaultReader constructor can only accept readable streams that are not yet locked to a reader
```

读代码后确认成因：`QA.tsx` 先 `stream.getReader()`（为了拿到 `readerRef`
以便 `stopActiveStream` 停流），**随后又把同一个 `stream` 交给
`parseSSEStream`**，而那个函数内部**再取一次** `getReader()` —— 读取器是独占的，
第二次必然抛错。`NoteAskPanel.tsx` 是**同一处缺陷的第二个副本**（同样的两行）。
后果：`智能问答` 这条功能**每次提问都直接失败**（错误文案是一句底层报错，
用户看不出发生了什么）。

**为什么以前没有任何一层发现它**：它是**运行期**的错误，`tsc` 看不见
（两个参数类型都对）、单测没覆盖这条路径、而审计此前**根本没有 `qa` 场景**
—— 就算有，如果不真的点一次「提问」，页面是空状态、"0 违规"、一切正常。

**修法**（`src/utils/sse.ts` + 两个调用点）：`parseSSEStream` 的入参改成
**"流或读取器"**，给流就自己取（调用方不需要停流，例如 `useStreamAnswer`），
给读取器就直接用（调用方需要停流，例如 `QA` / `NoteAskPanel`）。
"谁取的谁负责 `cancel`/`releaseLock`"写成了契约注释 —— 这比"两种写法都行"更准确，
因为它规定了所有权。修完 `qa` 场景扫通（121 个 DOM 元素、0 违规）。

### 10.7 F-36 的断言与两次变异测试（证明它真的会咬）

for (const m of priorityBadges) {

  // ★ 断言的是**阈值**（按字号/字重算出的 WCAG AA 门槛，这里是 4.5:1），

  expect(m.ratio, `${m.text}（优先级徽章）：实测 ${m.ratio}:1 < 要求 ${m.required}:1…`)

`1 failed`，报 `中（优先级徽章）：实测 2.16:1 < 要求 4.5:1`。

   要么接受；并且页面自己的「清洗统计」区块（`h4`）需要一个单独的决定。
   **不要**为了消警告去改用户内容。
5. **`LearningGoals` 新建目标弹窗**：`role="dialog"` / `aria-modal` / Esc /
   `htmlFor` 四件事都没做（打开弹窗才渲染，本轮没有为它加场景）。
   要不要把它们做成"审计也扫弹窗状态"的第二个场景，是范围决定。
6. **`KnowledgeCards` 等页的 `div[onClick]` 控件**（分组头、卡片本体、引用来源行）：
   要不要照 F-09/F-17 的形状改成真按钮/真链接。axe 判不了这一类，
   改了也没有门禁守着（除非同时写几何/键盘断言，见 §4.1）。

### 10.10 一句话结论

**这一轮把"能涨的数字"变成了"能降的数字"**：上场时是 12 组债 / 15 个节点 /
10 个没扫过的页面，收场时是 **5 组债（全是同一个待人工决定的问题）/
0 个没扫过的页面**，而且顺手在从没被真正执行过的路径上抓到一个
**每次提问都会失败**的功能缺陷（§10.5）。
最值得记住的一条仍然和上一轮一样：**"这次没报出来"不等于"没问题"** ——
它可能只是**没有被渲染过**（F-28/F-29）、**没有被真的点开**（§10.2 的四个交互）、
**桩的字段名/路径写错了**（§9.2 第 3 条 / §10.4）、或者
**axe 按设计拒绝判断**（F-36 的单字符文本，§9.4/§10.7）。
