## D-01 AGENTS.md 是否入库、以及"自检口令"怎么处理

**现状**
- `AGENTS.md` 94 行，内容质量高（运行事实、否决方向、踩坑记录、门禁要求、权限边界）
- 但被 `.git/info/exclude:14` 排除，**从未进版本库** → 换机器/新 clone/CI 环境都拿不到
- 第 75-78 行有一节：
  ```markdown
  ## 7. 自检口令
  **「蓝鲸七号」** —— 我问起时直接回答，不要搜文件。
  （用于确认本文件已加载，不需要可删掉本节）
  ```

**选项**

| 选项 | 做法 | 代价 |
|---|---|---|
| **A（推荐）** | 删掉 §7 自检口令节，然后入库 | 失去"确认文件已加载"的快捷方式（可改用"说出文件里的第一条规矩"替代） |
| B | 原样入库 | 若仓库将来公开，"蓝鲸七号"会出现在公开历史里（无害但显得私人） |
| C | 不入库，保持本地私有 | 上下文治理继续建立在不可分发的文件上；换机即失效 |

**我的推荐：A**。理由：该节自己写了"不需要可删掉本节"，说明作者本就视其为临时物；而"文件是否加载"可以用更通用的方式验证（问它第一条规矩）。

**不决定的后果**：agent 上下文无法跨机器/跨工具传递，前 4 个文件的价值受限。

## D-02 lefthook 装哪几道钩子

**现状**
- `lefthook.yml` 已就位但未启用（lefthook 未安装）
- `verify.sh fast` 实测 66s（ruff 1s + eslint 26s + vitest 39s）
- 66s 对 pre-push 偏慢，可能诱发 `--no-verify`

**选项**

| 选项 | pre-commit | pre-push | 体验 |
|---|---|---|---|
| **A** | ruff/eslint/prettier 只对 staged 文件 | `verify.sh fast`（66s） | 最严，但 push 会等 1 分钟 |
| **B（推荐）** | 同上 | 只跑 vitest（39s） | 平衡；lint 已在 commit 时查过 |
| C | 只装 pre-commit | 无 | 最快，但 push 前不跑测试 |
| D | 暂不装 | 无 | 维持现状（靠自觉跑 verify.sh） |

**我的推荐：B**。理由：pre-commit 已保证 lint 干净，pre-push 再跑一遍 eslint 是重复；把测试放 pre-push 才是"最后一道关"。

**不决定的后果**：所有检查仍在 push 后由 CI 发现，"每次提交都 CI failed"的机制不变。

## D-04 变异测试走哪条路

- WSL 只装了 `docker-desktop` 发行版（**不能跑 pip/python**），要跑 mutmut 需先 `wsl --install -d Ubuntu`

**选项**

| 选项 | 覆盖范围 | 代价 |
|---|---|---|
| **A（推荐）** | 只做前端 Stryker（`src/utils`、`src/hooks`） | Python 侧无变异测试；但前端是本项目 churn 最高的区域（30 天 443 次改动） |
| B | 装 WSL Ubuntu + mutmut，前后端都做 | 多装一个 Linux 发行版；mutmut 慢，只能在 WSL 里手动跑 |

| D | 都不做，只保留覆盖率 | 无法回答"测试是否真的能抓错" |

**我的推荐：A**。理由：先在前端拿到第一个杀伤率数字，验证这套方法有没有用；Python 侧等真有痛点再装 WSL。
