## 2. 环境前置（不满足会得到**假失败**）

**这是最容易浪费半天的地方。** 两个环境变量/PATH 不满足时，报错内容看起来像代码问题，实际是环境问题。

```powershell
# 1) Python 必须指向装了 ruff/pytest 的环境，不能是 base
$env:PYTHON = "D:\conda\envs\aiforlearn\python.exe"

# 2) gitleaks 必须在 PATH（pre-commit 的 secrets 步骤需要）
$env:PATH = "$env:PATH;$env:LOCALAPPDATA\Microsoft\WinGet\Packages\Gitleaks.Gitleaks_Microsoft.Winget.Source_8wekyb3d8bbwe"

# 3) 自检
& $env:PYTHON -m ruff --version
gitleaks version
```

**症状对照**：

| 报错 | 实际原因 |
|---|---|
| `No module named ruff` / `No module named pytest` | `python` 指向了 `D:\miniforge3\python.exe`（base 环境） |
| `sh: line 1: gitleaks: command not found` / `exit status 127` | gitleaks 不在 PATH |
| `git ... exit status 128`（钩子里） | 早期版本的 `git add {staged_files}` 问题，已修（`stage_fixed`） |

## 3. 六段式执行规范

### 3.1 先读什么（顺序不能乱）

1. `AGENTS.md` —— 尤其 **§3.5 环境与命令**（我刚补的七条命令）与 **§2 已否决方向**
2. `_governance/05-执行日志.md` —— 最近三轮决策与七个坑
3. 与任务相关的 `docs/`：架构看 `docs/architecture.md`，运维看 `docs/operations.md`，
   当前主线计划看 `docs/overhaul-plan.md`（**这是唯一权威**，`docs/decisions.md` 已声明只读归档）
4. 你要改的那个文件**同目录的既有写法**

**不要**先读 `_governance/02-改动记录.md`（那是第 0 批的过程记录，对改代码没用）。

### 3.2 怎么定范围：用规则判断，不要凭感觉

```bash
node scripts/risk.mjs --files <你打算改的文件...>
```

| 分数 | 档位 | 要求 |
|---|---|---|
| <20 | LOW | lint + 单测即可，可直接改 |
| 20–50 | MEDIUM | 改完必须跑 `verify.sh fast`，并在报告里贴结果 |
| >50 | HIGH | **先出方案再动手**；改完除 `fast` 还要跑覆盖率；必须写回滚方式 |

**首次修改请选 LOW 区**（`docs/`、`_governance/`、`backend/tests/`、`frontend/e2e/`、`scripts/`）。

### 3.3 怎么改

- **单一意图**：一个提交只做一件事。混了格式化或无关重命名，会被要求拆开
- **不顺手重构**：看到坏味道记下来，单独提，不要在同一次改动里修
- **不新增依赖**：真要加，先停下问人（会改 `package.json` / `requirements*.txt`，属于架构决策）
- **遵守既有约定**：命名、日志字段、错误处理方式都跟着同目录走，不要套通用最佳实践

### 3.4 怎么验证

```bash
bash scripts/verify.sh fast     # 约 41s：ruff + eslint(缓存) + vitest。日常够用
bash scripts/verify.sh full     # 会加 pytest（1760 用例 / 约 32 分钟）——除非改后端逻辑，别跑
```

**只改文档**时不必跑 `full`；**只改前端**时 `fast` 已覆盖 lint + 单测。

### 3.5 怎么提交（钩子会咬人）

```bash
git add <具体文件，不要 -A>
git commit -m "type(scope): 一句话说清为什么"
```

- **pre-commit 会跑 5 个步骤**，约 1s。它会**自动修复** import 排序与格式并重新 stage
- 遇到 `F821 Undefined name` 这类**不可自动修复**的问题才会真正拦住——这是对的，照改
- **不要用 `--no-verify`**。如果钩子因为环境问题失败（见 §2），先修环境，不要绕过
- **不要 `git add -A`**：工作区可能有别人的未跟踪产物。本仓库有过"`git add -A` 会把内部工作流推上去"的教训（见 `docs/open-source-readiness.md` §4.3）

### 3.6 什么时候必须停下来问人

- 删数据/文件（**尤其 `backend/data/`**——那是真实笔记，不是夹具）
- 装占磁盘的东西（模型权重、新依赖）
- 改产品语义或接口契约（`backend/app/api/`、`schemas/`、`openapi.json`）
- 推翻 `AGENTS.md` §2 的既定决策
- 需要动 `alembic/versions/` 已有迁移（只能新增，不能改历史）

## 5. 七个已踩过的坑（别重踩）

| # | 坑 | 症状 | 正确做法 |
|---|---|---|---|
| 1 | 用 base 环境的 python | `No module named ruff` | 设 `PYTHON` |
| 2 | gitleaks 不在 PATH | `exit status 127` | 加 PATH 或重启终端 |
| 3 | `.ps1` 存成无 BOM UTF-8 | PowerShell 按 ANSI 解码 → 中文乱码 → 报错行号完全漂移 | `.ps1` 必须带 BOM；`.json` 必须**不**带 BOM |
| 4 | 覆盖率配置放根 `pyproject.toml` | 配置"写了但没生效"（TOTAL 不变） | 放 `backend/.coveragerc` |
| 5 | 变异测试配置放仓库根 | Stryker 静默退化为默认 runner，只发现 1 个测试 | 放 `frontend/stryker.config.json` |
| 6 | 对没有测试的文件跑变异 | 变异体全 timeout | 先确认有 `*.test.ts` |
| 7 | `git add -A` | 会把未跟踪的私有产物一起提交 | 只 add 具体路径 |
| 8 | **在 MD 表格行末尾追加内容** | 加在结束符 `\|` **之后** → 该行多一列，`docs:tables` 报"表头 5 列、本行 6 列" | 追加内容要放在结束符 `\|` **之前**；或另起一行写注记（但会让后续行号漂移，谨慎） |

## 5.5 「改名」是一次影响面变更，不是一次改动

这一轮的真实教训：把 CI job `docker-nginx-config` 改名为 `nginx-config-guard` 后，**5 处活文档仍在引用旧名**，其中 1 处是当前唯一权威的 `docs/overhaul-plan.md`。

**改名时必须同步检查的四类引用**：

```bash
# 1) 活文档与代码注释
git grep -n '<旧名>' -- '*.md' '*.py' '*.ts' '*.yml'
# 2) CI 与分支保护（分支保护里的 required check 在 GitHub 设置里，本地看不到）
# 3) 脚本与配置
git grep -n '<旧名>' -- 'scripts/' '.github/'
# 4) 历史快照文档（不改结论，只加"已改名"注记）
```

**处置原则（按文档性质分）**：

| 文档性质 | 处置 |
|---|---|
| 活文档（README / CONTRIBUTING / overhaul-plan） | **改名 + 标注原名**，行号引用一并更新 |
| 历史快照（open-source-readiness 等核查报告） | **不改结论**，只追加"该 X 已于 YYYY-MM-DD 改名" |
| `_governance/` 的记录 | 保留旧名（那是历史事实） |

**还有一处本地看不到的风险**：如果 GitHub 的分支保护把旧 job 名列为 required check，改名后该 check 会一直 pending，PR 永远合不了。**改用新名前，先去仓库 Settings → Rules 确认 required checks 列表。**

## 7. 出问题怎么收

```bash
# 看改了哪些
git status --short
git diff --stat

# 退回某个文件
git checkout -- <path>

# 退回最近一次提交（保留改动）
git reset --soft HEAD~1

# 彻底回退一次提交
git revert <sha>
```

**总原则**：每条改动都是独立提交，任何一条都能单独 `revert`。如果你发现需要"一次撤销一大片"，说明提交粒度不够，下次拆细。
