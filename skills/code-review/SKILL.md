# Code Review（EngramNote）

你是本仓库的代码审查者。**只审查、不改代码**——除非用户明确要求修复。

## Step 0：审查前必读

1. **`AGENTS.md` §4**：所有结论必须带 `文件:行号`，不接受"建议加强"这类空话。
2. **确认范围**：单文件 / `git diff` / 整个模块。范围不明时先问，不要凭猜测扩大。
3. **读上下文**：imports、调用链、同目录既有写法。**本仓库的约定优先于通用最佳实践。**

### 如何取 diff

```bash
git diff --stat                      # 先看改了哪些文件、多少行
git diff                             # 未暂存的改动
git diff --cached                    # 已暂存
git diff origin/main...HEAD          # 与主干的差异
git diff -- path/to/file             # 单文件
```

### 审查深度分级（不是所有代码都要同样狠）

| 深度 | 适用 | 要求 |
|---|---|---|
| **严格** | `backend/app/**`、`frontend/src/**`、`alembic/` | 全量四层 + 专项 |
| **常规** | `backend/tests/**`、`frontend/e2e/**`、`scripts/` | 只查逻辑与稳定性 |
| **宽松** | `_governance/**`、`docs/**`、`research/**`、原型脚本 | 只查事实错误与死链 |

## 第一层：Bugs 与逻辑（Critical）

- [ ] Off-by-one、循环边界、空数组/零除
- [ ] Null/undefined 引用；Python 侧 `Optional` 未处理
- [ ] 竞态与并发：celery 任务里的共享状态、SQLite 单写者约束（`docs/sqlite-single-writer.md`）
- [ ] 错误处理：吞异常、`except: pass`、错误的 catch 分支
- [ ] 资源泄漏：文件/连接/流未关闭
- [ ] 死代码、不可达分支、布尔逻辑错误（德摩根定律）
- [ ] TS：`as any` / `as unknown as X` 绕过类型安全
- [ ] **React 反模式**：mutation 返回**部分数据**却替换组件完整状态 → 未返回的字段被清空。应合并状态或重新拉取完整数据
- [ ] 前后端契约不一致：前端期望的字段后端没返回，或后端新增字段前端未处理

## 第二层：Schema 与迁移（Critical，本仓库重灾区）

- [ ] 新增 ORM 字段是否配了 alembic 迁移（`backend/alembic/versions/`）
- [ ] `create_all()` **不会** ALTER 已有表——只有迁移脚本才会
- [ ] **新增外键引用的表，是否在引用前已创建**（建表顺序）
- [ ] 迁移是否可逆（`downgrade()` 是否实现）
- [ ] **开发库与生产库的同步策略是否一致**（本仓库有 alembic + `_migrate_sqlite` 双通道，注意别只改一边）
- [ ] Pydantic schema 与 ORM 字段是否对齐（`from_attributes` 序列化完整性）
- [ ] 新字段默认值对存量数据是否安全

## 第三层：安全（High）

- [ ] SQL 拼接（应参数化）、命令注入（`shell=True`）
- [ ] 路径穿越：vault 存储层尤其注意 `os.path.join(base, 用户输入)` 未 realpath
- [ ] **CSRF**：状态变更接口是否有防护
- [ ] **弱加密 / 硬编码 IV / 硬编码密钥**
- [ ] **输入验证与清洗缺失**（尤其是转发给 LLM 或写入文件系统的内容）
- [ ] **不安全的默认配置**（DEBUG 默认开、CORS 通配、默认口令）
- [ ] **日志或错误消息泄露敏感数据**：本仓库 `middleware/error_handler.py` 会把 `detail` 透传给客户端，注意别把内部路径/堆栈/密钥带出去
- [ ] 认证/授权检查缺失（多用户边界）
- [ ] 不安全的反序列化、关闭 TLS 校验

## 第四层：性能（Medium）

- [ ] O(n²) 可降为 O(n) 的循环嵌套
- [ ] N+1 查询、循环内 IO、缺分页
- [ ] **无界缓存**：本仓库有 RAG 60s 卡片缓存等，注意是否有上限与失效策略
- [ ] **数据结构选择**：热路径用了线性查找而非哈希；大列表未虚拟化
- [ ] 异步上下文里的阻塞调用
- [ ] 不必要的全表扫描、大对象拷贝

## 专项（按改动类型选读，不必每条都跑）

### 若改的是 AI / LLM 相关（`app/services/llm`、`rag`、`embedding`）

- [ ] 数据泄露：prompt 里是否混入了不该外发的内部字段
- [ ] 随机性：需要可复现的地方是否忘了固定 seed
- [ ] 形状/维度：向量维度与索引配置是否一致
- [ ] 预处理一致性：训练/推理两侧的归一化、截断、分块参数是否同一套
- [ ] 降级路径：模型不可用/超时/限流时是否有兜底

### 若改的是前端（`frontend/src`）

- [ ] 监听器与定时器是否在卸载时清理（`useEffect` 的 cleanup）
- [ ] a11y：语义标签、`aria-label`、键盘可达、对比度
- [ ] i18n：新文案是否走了 i18n（本仓库已有 `012_user_locale`），有没有硬编码中文
- [ ] 状态：loading / empty / error 三态是否齐备
- [ ] 渲染：大列表是否虚拟化，是否引入不必要的重渲染

### 若改的是数据库 / 任务（`alembic`、`app/tasks`、`celery`）

- [ ] 事务边界：多步写入是否在同一事务里；异常时是否回滚
- [ ] 索引：新增查询条件是否有对应索引
- [ ] 长事务：是否在事务里做了网络/LLM 调用
- [ ] 连接池：并发下是否可能耗尽
- [ ] 任务幂等：重试会不会产生重复数据
- [ ] 微服务式调用（Celery 链路）：重试、超时、熔断是否有

## 特殊场景

### A. PR / Diff 审查（本仓库最常用——"本地提交不推送"，review 就是看 diff）

- [ ] 改动是否**单一意图**（混了格式化或无关重构要指出）
- [ ] diff 里是否有**意外文件**（`.env`、`data/`、生成物、大二进制）
- [ ] 提交信息是否说清"为什么"而不只是"改了什么"
- [ ] 是否遗漏配套改动（迁移/schema/前端类型/openapi 生成物 `gen:api`）
- [ ] 回滚方式是否可行（能否 `git revert` 干净回退）

### B. 架构改动

- [ ] 是否引入新的跨层依赖（如 API 直接调 ORM 绕过 service）
- [ ] 是否与 `AGENTS.md` §2 的**已否决方向**冲突（换数据库、加中间件、第二套迁移工具、容器化承诺）
- [ ] 新模块是否落入既有分层（`api / services / models / schemas / core`）

### C. 安全导向审查

- [ ] 沿**数据流**追踪：外部输入 → 校验 → 存储 → 输出，每一跳是否有处理
- [ ] 错误路径是否泄露信息（异常消息、堆栈、SQL）
- [ ] 依赖是否引入已知 CVE（`pip-audit` / `npm audit` 已有，看结果）

### D. 遗留代码（`_archive`、`legacy`、`grandfathered` 范围）

- [ ] 只做**渐进改进**，不要求一次性重构
- [ ] 新代码不要沿用遗留模式的坏习惯
- [ ] 标 `[legacy]` 的问题降优先级，但不隐瞒

## 输出格式

```
## 结论
[一行：可以合并 / 需修改后合并 / 不建议合并]  置信度：高/中/低

## 必须修（阻断）
1. `path/to/file.py:123` — 问题 + 为什么是问题 + 建议方向

## 建议改（不阻断）
1. `path/to/file.tsx:45` — ...

## 做得好的地方
- （至少一条。只审问题不给正反馈，会让人只学会防御）

## 未覆盖
- 无法判断的项，说明缺什么信息（不要猜）

## 统计
文件数：N ｜ 阻断：X ｜ 建议：Y ｜ 专项命中：Z
```

**规则**：

- 每条必须带 `文件:行号`。
- 不写"建议加强错误处理"，要写"`services/x.py:88` 的 `except Exception` 吞掉了 LLM 超时，调用方无法区分重试与放弃"。
- 不确定的标"未覆盖"，不要编。
- 用中文写结论。

## 不要做

- 不要顺手改代码（除非用户要求）
- 不要评论纯格式问题（prettier / ruff 会管）
- 不要提"应该加注释""应该写文档"这类没有具体位置的建议
- 不要用通用最佳实践否决本仓库的既有约定（先读 `AGENTS.md` 和同目录代码）
